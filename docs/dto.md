# DTO 규약

## 요청 · 응답 DTO

- 요청·응답 DTO는 **`record`로 만든다.** 클래스로 만들지 않는다
- 이름은 엔드포인트를 기준으로 짓는다. `<도메인><행위>Request` / `<도메인><행위>Response` (`naming.md`)
- **엔티티를 `@RequestBody`나 응답에 직접 노출하지 않는다.**
  LAZY 직렬화 사고가 나고, API 스펙이 DB 스키마에 묶인다
- 응답 조립은 응답 record의 정적 팩토리에 둔다.
  엔티티 하나로 조립할 수 있으면 이름은 `from(<엔티티>)`로 짓는다

## record의 `toString()`

- 로그에 남으면 안 되는 값을 필드로 가진 요청 record는
  **`toString()`을 직접 오버라이드해서 그 필드를 마스킹한다.**
  `lombok.config`가 막는 것은 `@ToString`이고 record가 만드는 `toString()`은 막지 못한다
- 요청 record를 통째로 로그에 넘기지 않는다 (`logging.md`)

## 검증은 2층

| 층 | 대상 | 수단 |
|---|---|---|
| 형식 | 필드 하나만 보고 판단할 수 있는 것 (필수 여부, 길이, 미래 시각, 값의 범위) | 요청 DTO 필드의 Bean Validation + 컨트롤러 `@Valid` |
| 상태 | 다른 행을 조회해야 아는 것 (정원 초과, 중복 등록) | 서비스 |

- Bean Validation은 다른 행의 상태를 모르기 때문에 서비스층을 대신할 수 없다
- 반대로 **같은 필드를 두 층에서 검사하지 않는다**
- 제약 애노테이션의 `message`에 `${validatedValue}`를 쓰지 않는다.
  거부된 입력값이 검증 실패 로그를 타고 나간다 (`logging.md`)

## 엔티티 컬럼에 맞추는 DTO 필드 범위

요청 DTO의 값이 엔티티 컬럼에 그대로 저장되면, DTO의 제약은 그 컬럼의 제약을 넘지 않게 맞춘다.
새 요청 DTO를 쓸 때 필드가 저장될 엔티티를 먼저 찾아서 대조한다.

- 엔티티에 `@Column(length = ...)`가 있으면 대응 필드에 그 값 이하의 `@Size(max = ...)`를 둔다.
  DTO 쪽 상한이 더 크거나 없으면 Bean Validation은 통과하고 저장 시점에 DB가 값을 자르거나
  예외를 던진다. Bean Validation 통과가 저장 성공을 보장하지 않는다
- 엔티티에 `@Column(nullable = false)`가 있으면 대응 필드에 `@NotBlank`(문자열) 또는 `@NotNull`을 둔다
- 엔티티 컬럼에 매핑되지 않는 값(해시로 변환해 저장하거나, 저장 없이 그대로 위임하는 값)은
  대응할 컬럼이 없다. 이때 상한은 그 값이 실제로 낼 수 있는 형식·프로토콜상의 길이로 잡는다
